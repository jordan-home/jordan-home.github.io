系统设计题是前端面试的高地。这篇文章梳理答题框架。

## 答题框架

### 1. 明确需求

- 功能需求：要做什么
- 非功能需求：性能、可用性、一致性、扩展性

### 2. 估算规模

- QPS：日活 * 每个用户每天请求数 / 86400
- 存储：1 年数据量 / 单机容量

### 3. 高层设计

- 画架构图：客户端 → API → 服务 → DB
- 关键模块拆解

### 4. 深入细节

- 关键算法
- 数据模型
- 性能瓶颈

### 5. 权衡取舍

- 选 A 的理由
- 替代方案 B、C 的优缺点

## 经典题

### 1. URL 缩短服务（bit.ly）

需求：
- 长 URL → 短 URL
- 短 URL → 302 跳转 / 直接渲染长 URL 内容

设计：
- Hash 算法：长 URL → 6 位 base62
- DB 存短-长 + 创建时间 + 过期时间
- 缓存：热门短 URL 进 cache

深入：
- 分布式 ID 生成（Snowflake）
- 防刷（限流）
- 统计点击数

### 2. Feed 流（推 / 拉）

需求：
- 用户关注的人的更新按时间倒序展示

设计：
- 拉模式：读时聚合
- 推模式：写时 fanout
- 混合：明星推 / 普通人拉

深入：
- 分页（游标 vs 偏移）
- 缓存策略
- 数据一致性

### 3. 抢票 / 秒杀

需求：
- 1000 库存，10 万人抢

设计：
- 限流：Nginx / Redis 漏桶
- 库存预热到 Redis
- 原子扣减：Redis Lua
- 异步下单：消息队列

深入：
- 防超卖（数据库乐观锁 / Redis 原子操作）
- 黄牛识别（IP / 设备指纹）
- 公平性

### 4. 限流

需求：
- 单用户每秒最多 100 个请求

设计：
- 令牌桶：周期性发放令牌
- 漏桶：固定速率流出
- 滑动窗口：时间窗内计数

深入：
- 分布式限流（Redis + Lua）
- 限流粒度（用户 / IP / 接口）
- 熔断降级

## 实战建议

### 1. 不要背答案

理解问题本质，每个系统的设计都不同。

### 2. 多画图

白板画图能力 = 系统设计能力的体现。

### 3. 主动说权衡

没有完美方案，每个选择都有代价。**说出"为什么选 X 而不是 Y"** 才是高分答案。

### 4. 关注业务

脱离业务的系统设计 = 纸上谈兵。

## 准备方法

- 自己画 5-10 个常见系统的架构图
- 看完再默画一遍
- 跟朋友讨论，互相提问

系统设计是**经验的语言化**。设计过 10 个真实系统，比刷 100 道题有用。
