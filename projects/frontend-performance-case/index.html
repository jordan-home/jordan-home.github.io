前端性能优化案例研究

前端性能诊断与优化方法论：代码分割、懒加载、缓存策略。

角色
实践项目
时间
2026

· 技术栈 ·

  • Next.js 14
  • Webpack 5
  • Chrome DevTools
  • Lighthouse CI

背景

在优化 SweetNovel 前端性能时，我记录了一套完整的性能诊断 + 优化方法论。这套方法后来被应用到多个内部项目中。

问题诊断

初次审计暴露出一系列典型性能问题：首屏内容渲染偏慢、最大内容绘制延迟、页面交互准备时间过长、主线程阻塞明显、布局存在偏移——这些都是内容型站点最常见的性能瓶颈。

优化步骤

Step 1: 代码分割（Bundle Split）

问题：主 bundle 包含所有页面代码，首屏需要加载大量 JS，明显拖慢渲染。

解法：

// next.config.js
module.exports = {
  webpack: (config, { isServer }) => {
    if (!isServer) {
      config.optimization.splitChunks = {
        chunks: 'all',
        cacheGroups: {
          vendor: {
            test: /[\\/]node_modules[\\/]/,
            name: 'vendors',
            chunks: 'all',
          },
          pages: {
            test: /app\/(browse|series|book)\//,
            name: 'page-',
            chunks: 'all',
          },
        },
      };
    }
    return config;
  },
};

结果：主 bundle 显著瘦身，首屏 JS 加载量大幅下降，渲染明显加快。

Step 2: 图片优化（Next.js Image）

问题：小说封面图未优化，图片体积偏大，拖慢关键资源加载。

解法：

import Image from 'next/image';

<Image
  src="/covers/book-1.jpg"
  alt="Book cover"
  width={300}
  height={450}
  placeholder="blur"
  blurDataURL="data:image/jpeg;base64,..."
  loading="lazy"
/>

结果：图片体积大幅下降，关键视觉内容（LCP）加载明显改善。

Step 3: 字体优化（font-display: swap）

问题：自定义字体加载中导致 FOIT（无字体闪烁）。

解法：

@font-face {
  font-family: 'Noto Serif SC';
  src: url('/fonts/noto-serif-sc.woff2') format('woff2');
  font-display: swap;
  unicode-range: U+0000-00FF, U+0100-017F, U+4E00-9FFF;
}

结果：首屏文本立即可见，消除了字体加载造成的空白等待，感知加载速度明显提升。

Step 4: 缓存策略（Cache-Control）

问题：API 请求重复拉取，网络请求过多。

解法：

// middleware.ts
export function middleware(request: NextRequest) {
  const response = NextResponse.next();
  
  // API 缓存 1 小时
  if (request.nextUrl.pathname.startsWith('/api')) {
    response.headers.set('Cache-Control', 'public, s-maxage=3600');
  }
  
  // 静态资源长期缓存
  if (request.nextUrl.pathname.match(/\.(js|css|png|webp)$/)) {
    response.headers.set('Cache-Control', 'public, max-age=31536000');
  }
  
  return response;
}

结果：重复访问时大幅减少重复请求，带宽显著节省。

Step 5: React Server Components

问题：客户端水合（hydration）耗时长。

解法：将非交互组件升级为 Server Component：

// app/books/[slug]/page.tsx (Server Component)
export default async function BookPage({ params }) {
  const book = await fetchBook(params.slug);
  return <BookDetail book={book} />;
}

结果：客户端 JS 大幅减少，页面更快达到可交互状态。

最终结果

经过上述优化，性能审计中的核心指标——首屏内容渲染、最大内容绘制、可交互时间、布局稳定性——均得到明显改善，整体加载体验显著提升。具体的量化结果记录在私有仓库的前后对比 demo 与 Lighthouse CI 配置中（见代码位置）。

方法论总结

  1. 先测量，后优化：用 Lighthouse + WebPageTest 建立基线
  2. 关注 Core Web Vitals：FCP/LCP/CLS/INP 是 Google 核心指标
  3. 代码分割优先级：vendor > pages > components
  4. 图片优化是低成本高收益：Next.js Image 组件开箱即用
  5. 缓存策略分层次：CDN > Service Worker > HTTP Cache
